How it works

Docker is optional. A service that declares a command runs as a local process with only your app's runtime. For a container stack, Docker runs the containers, Tilt watches services and live-updates containers as you code, and Flisk CLI writes the configuration Tilt uses.

Honest answers

The same answers we give in engineering reviews.

>We need Kubernetes for production
Local dev doesn't need to match production. The 14 tiny services were healthy in 4.6s on a 16 GB M1 after images existed. Not a cold boot. Production stays on Helm. Claim details.
>What about CI/CD?
Flisk is completely decoupled from your CI. Use it for local development and whatever you want for CI/CD. Nothing to migrate away from later.
>Is {{ site.data.flisk.scale_plain }} services locally realistic?
As a boot test, yes: this generated /health fixture has {{ site.data.flisk.scale_plain }} small generated services (about 20 lines each) that all became healthy through Traefik in {{ site.data.flisk.erp_boot_seconds }} s on a clean CI runner, images built from scratch (the run). It is a scale fixture, not a real ERP product. Real services with real dependencies use more memory. Selective startup runs only what you're working on, and golden L1–L4 layers keep rebuilds near-instant. The discovery daemon regenerates only what changed. Our daily driver is a {{ site.data.flisk.demo_services }}-service stack on a {{ site.data.flisk.machine }}, and it performs superbly; the same engine runs a {{ site.data.flisk.monorepo_services }}-service monorepo every day.
>Where do the savings numbers come from?
The calculator uses inputs you set. Its output is arithmetic, not savings. The starting value of five hours per week is only an editable input, not a typical measurement. We make no savings claim for your team.
