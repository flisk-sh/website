Getting started

>Do I need Kubernetes to run Flisk?
No. Flisk runs on your computer with Docker and Tilt, and a service that sets a command runs as a plain local process with no Docker at all. Flisk does not write Kubernetes manifests by default. Production stays with the tools you already use. See Use with Helm for how the two sit side by side.
>Do I need Docker?
Only for container stacks. Docker is optional: a service with a command in its service.json starts as a local process. Read Run without Docker ↗ for what that covers. If Docker is not running, flisk demo falls back to a two-service app as local processes.
>How do I add Flisk to an existing repo?
Run flisk import in a repo that has a root docker-compose.yml. It writes a service.json for each service, and --dry-run shows the result first. Without a compose file, run flisk project and then flisk resource for each service. The migration page walks through both.
>What does Flisk cost?
Flisk core is free and MIT licensed, and it needs no key to run. Premium is a separate license for extras such as Playwright and C4 diagrams, at ${{ site.data.flisk.team_price }} per developer per month. You do not need it to follow any page in these docs. See pricing.

Files and lock-in

>Which files does Flisk generate?
You write one service.json per service. From it Flisk generates the Dockerfile, the Compose entry, the Traefik routes, the health check and the Tiltfile. They are written under .flisk/ and .flisk-out/, and file names ending in autogenerated are Flisk's. Do not edit them by hand: change the service.json and let Flisk write them again. How it works shows the flow.
>What happens if we leave Flisk?
Your own Dockerfiles, service.json files and code are never touched. Run flisk eject and it writes EJECTED.md, which says where the generated files are and how to run the stack with plain tilt up. It copies nothing; the files stay where they are. More on the no lock-in page.
>Does Flisk deploy my app?
No. Flisk is for local development and does not deploy anything. Three opt-in commands write files for you to use elsewhere: flisk export render writes render.yaml, flisk export wrangler writes wrangler.toml, and flisk export compose writes a standalone docker-compose.yml. They never call a cloud API, never create DNS records, and write environment variable names, never values.

Daily use

>How do I run database migrations?
Give the migration its own resource with appType: migrator, not a step in your API's start script or entrypoint. That keeps the API's start fast and makes the migration a step you can run and read on its own. The next-postgres starter shows it: flisk create myapp --starter next-postgres writes a migrator that creates and seeds the table.
>How do I use Flisk in CI?
Copy the workflow in Running Flisk in CI ↗. Its light job runs flisk project --yes, flisk doctor --no-ping and flisk config verify to check the committed files without starting a container. Its heavier job runs flisk up and waits for each service's /health.
>What is the difference between flisk doctor and flisk config verify?
flisk doctor checks your environment and your services. flisk config verify checks that the generated files in the project match your service.json files. Run doctor when something will not start, and config verify when files may be out of date.
>Something does not start. Where do I look?
Run flisk doctor first, then flisk status to see which service is unhealthy and flisk logs for its output. The troubleshooting page lists common failures and their fixes.

AI agents

>How do AI agents use Flisk?
Over MCP. Add { "command": "flisk", "args": ["mcp"] } to your agent's MCP settings and it can create resources, start the stack, read status and logs, and check the generated files. Flisk also has an agent resource type for a long-running agent with sessions that survive restarts. See AI agents and skills.
