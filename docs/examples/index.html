Examples & reference landscapes

Example repositories demonstrating the Project-Stack-Resource (PSR) model in action.

Official reference repositories

Clone and run these complete Flisk landscapes locally with a single command via the Flisk CLI:

terminal
flisk project example          # base reference stack
flisk project user-management  # enterprise governance demo
flisk project erp              # 100-service scale fixture
flisk project restaurant       # restaurant ops demo
flisk project saas             # SaaS dashboard + checkout starter

Each one clones straight into ./<name> (use --path <dir> to pick a different folder), so you're one cd and flisk up away from a running stack. Prefer plain git? Use the links below instead:

A Vue storefront

flisk resource storefront-web --type frontend --framework vue --stack store writes "framework": "vue" into the manifest. That one field makes Flisk generate the Vue Vite config and a TypeScript config without React's JSX setting. Docker, nginx, Traefik and Tilt are shared with React frontends.

Managed services, run locally

Each managed service is an ordinary resource or container, and the app depends on an interface, not on a vendor. reports-api checks tokens against a JWKS URL, so pointing it at a real tenant is a params change. The Queue interface has a NATS implementation and redelivers a job when the worker fails. The Mailer sends SMTP into Mailpit, which shows what a recipient would get.

The stand-ins are not the real services: the emulator is not a security product (hard-coded users, no MFA or redirect flow), and JetStream differs from SQS in ordering and dead-letter behavior. The README lists what it does not do.

Manifest patterns

These manifests aren't from a reference repo. They're short patterns that use only fields the engine reads. The configuration reference lists every field.

Frontend and backend

dependsOn starts catalog-api before the frontend and writes its URL into the frontend's generated env. basePath serves the app at /shop.

services/storefront/web-app/service.json
{
  "appName": "web-app",
  "appType": "frontend",
  "stack": "storefront",
  "port": 3000,
  "basePath": "/shop",
  "dependsOn": ["catalog-api"]
}
services/storefront/catalog-api/service.json
{
  "appName": "catalog-api",
  "appType": "backend",
  "stack": "storefront",
  "port": 4000,
  "featuresEnabled": ["prisma"],
  "dependsOn": []
}

Workers with replicas

replicas: 3 runs transcode-worker-1 to -3. The schema requires workers to enable nats. The workers list media-migrator in dependsOn, so the Prisma migrations run before any worker starts.

services/media/transcode-worker/service.json
{
  "appName": "transcode-worker",
  "appType": "worker",
  "stack": "media",
  "port": 4300,
  "featuresEnabled": ["nats", "redis"],
  "dependsOn": ["media-migrator"],
  "replicas": 3
}
services/media/media-migrator/service.json
{
  "appName": "media-migrator",
  "appType": "migrator",
  "stack": "media",
  "featuresEnabled": ["prisma"]
}

Start one stack

Pass a stack name to flisk up to start only that stack's resources. Add --dry-run to list them without starting anything.

terminal
flisk up media --dry-run   # list what would start
flisk up media             # start the media stack only

Project layout

Every reference repo uses the same shape: one folder per stack, one folder per resource. Discovery reads services/*/*, the path set in .flisk/project.json.

project layout
my-project/
├── .flisk/project.json            # discovery paths, phases, optional infra
└── services/
    ├── storefront/              # stack
    │   ├── catalog-api/         # resource
    │   │   ├── service.json
    │   │   └── .autogenerated/  # Dockerfile, tsconfig, Vite config, AGENTS.md
    │   └── web-app/
    │       └── service.json
    └── media/
        ├── media-migrator/
        │   └── service.json
        └── transcode-worker/
            └── service.json

Brownfield rescue

An existing monorepo with {{ site.data.flisk.brownfield_dirs }} service folders and only {{ site.data.flisk.brownfield_found }} manifests. For every folder without a service.json, discovery builds a manifest from the folder's path, so all of them boot. The output below is illustrative.

terminal (illustrative)
$ flisk up
[discovery] scanned {{ site.data.flisk.brownfield_dirs }} directories · {{ site.data.flisk.brownfield_found }} manifests found
[synthesis] {{ site.data.flisk.brownfield_synth }} manifests synthesized from structure
[generate] local files for {{ site.data.flisk.brownfield_dirs }} discovered services
[health] {{ site.data.flisk.brownfield_healthy }} resources healthy

Guidance for AI assistants

Each resource's .autogenerated/ folder gets an AGENTS.md that tells coding assistants the files there are generated and must be changed through service.json, not edited by hand. With the premium bundle, Flisk also writes a C4 model of the running topology to .tilt/c4-model.json.

generated files
services/<stack>/<resource>/.autogenerated/AGENTS.md  # don't-edit notice for assistants
.tilt/c4-model.json                                    # C4 model (premium)
